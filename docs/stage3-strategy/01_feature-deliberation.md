# 追加機能アイデア：チーム合議と実装方針（2026-06-20）

オーナー提示の追加アイデア群（①拡散 ②体験 ③収益 ④構造）を、専門家4名が評価。秘書が統合。

## 各専門家の結論
- 🛠 **テックリード**：今やるべき技術土台＝**「熱量🔥＋spaceId」をローカルに足す軽量スキーマ拡張**（確信度:高）。`item`に1〜2フィールド足すだけで将来の移行コストを消せる。共有シートはExpo Go不可＝EAS開発ビルドが必要でPhase2。BaaSはやるならSupabase（集計に強い）だが今は不要。実装順＝熱量→スペースの箱→スペースUI→Supabase→共有/集計→共有シート。
- 💰 **マネタイズ**：最初の収益導線＝**「ギフト共有用の公開ほしいものリストWebページ（アフィリ購入リンク付き）」**（確信度:80%）。第三者購入で自己アフィリ規約とApple3.2.2を同時回避＋口コミ。照合エンジン・価格追跡・登録簿は当面不要（過剰）。ASPは「もしも」で国内まとめ取り。LinkSwitchでWeb側収益完結は有効。試算：保守≒月270円／中間≒月8千円。
- 📣 **SNS/マーケ**：最初に賭ける拡散ループ＝**Wrapped（季節・診断シェア画像）**（確信度:高）。1人でも回る・実装軽い・ストーリーズ親和。少データでも「量」でなく「鏡（診断ラベル）」型にすれば成立。第2の矢＝推し活（タグ＋発売日通知）。ギフト/共同/トレンドは基盤が育ってからの“増幅装置”。
- 🔥 **専属批判家**：アイデアの8割（収益・共有・拡散）は**ユーザーと堀が無い今やると過剰設計**。真の課題＝「忘却に勝てた証拠＝**達成率**」が未検証。**堀＝共有シートを最優先**で実装/検証すべき。次の3手＝①共有シート保存②達成率の可視化③熱量🔥→通知優先度の軽い連動（収益・共有・拡散は凍結）。

## 収束と対立（秘書の読み）
- **全員一致で“今・軽い”＝熱量🔥**（体験の燃料・通知出し分け）。→ 実装済み。
- **批判家 vs マーケ/マネタイズ**：批判家「堀(共有シート)と達成率の証明が先、拡散/収益は凍結」 vs マーケ/マネタイズ「Wrapped/ギフト共有で拡散×収益を早く」。
  - 秘書の裁定：**批判家が正しい順序**。ユーザー不在で拡散/収益の配管を作るのは“回収先のない水道工事”。ただしWrappedは「自分の使用データで達成率を“鏡”にして見せる」形なら、**達成率の可視化＝批判家の#2 と Wrapped＝マーケの#1 は同じ一手で両立**できる（拡散は後でも、まず自分用の振り返りとして作れる）。
- **2つの“卒業”が重い機能のゲート**：
  - 卒業A：Expo Go → **EAS開発ビルド** ＝ 共有シート(堀)・OCR・ウィジェット・プッシュ解禁。
  - 卒業B：ローカル → **Supabase等BaaS** ＝ ギフトWeb公開・共有スペース・同期・トレンド解禁。
  - ほぼ全部の大型機能は A か B の後ろに並ぶ。

## 実装方針（軽い→重い）
1. ✅ **熱量🔥（1-3）**：保存/詳細で選択、通知の既定を出し分け、タイルに炎メーター、「本気」フィルタ＋並べ替え。（実装済み）
2. ✅ **達成率の可視化**：マイページに達成率％＋「本気で叶えた/気になっただけ」。（実装済み）
3. ⬜ **データの形を将来対応に**（軽量）：`item.spaceId='personal'` を静かに付与（移行コスト先払い・UIなし）。
4. ⬜ **Wrapped / 振り返りシェアカード**：自分の達成率・傾向を1枚画像に（まず自分用→将来シェア）。バックエンド不要・中量。
5. ⬜ **堀の検証：共有シート（EAS開発ビルド）** … 卒業Aの判断。最強の差別化だが初心者には重い。
6. ⬜ **ギフト共有Webページ＋アフィリ（Supabase）** … 卒業Bの判断。拡散×収益の本丸。
7. 🧊 **凍結（当面やらない）**：価格追跡・照合エンジン・登録簿・トレンドPR・共同リスト同期・スクショOCR一括（規模/サーバー/有料/卒業が必要）。
